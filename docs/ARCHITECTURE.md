# Architecture

Aura stores original bytes without rewriting them and maintains grouping and visibility separately. Normal removal and regrouping are reversible; confirmed permanent deletion removes selected trash items' live originals through durable cleanup. Upload completion is independent of preview generation, so accepted originals survive processing failures and remain downloadable while derivatives are repaired.

## Technology selection

| Component | Choice | Reason |
| --- | --- | --- |
| HTTP service | Go, chi | Streaming uploads/downloads, bounded media subprocesses, static deployment, explicit routing |
| Web application | React, TypeScript, Vite | Component-based library and viewer, worker-based checksums, modern browser file APIs |
| Catalog and durable work queue | SQLite with WAL | Indexed capture-date pagination and transactional grouping for a personal library; portable consistent snapshots |
| Image decoding and previews | libvips | Demand-driven decoding of HEIC and common image formats; full-resolution pixels can be hashed without keeping the entire library in memory |
| Metadata | ExifTool | EXIF, XMP, Apple MakerNotes, QuickTime, ICC, GPS, and camera-specific metadata |
| Video playback | FFmpeg, HLS, hls.js | Original-first playback with request-triggered H.264/AAC segments; original codecs and metadata remain intact |
| Apple import | SwiftUI, PhotoKit, URLSession | Direct original-resource access, capture-date queries, paired-video export, system-managed background transfers |

Immich was considered because it already provides a strong photo pipeline and native apps. Its documented root-domain requirement conflicts with the established path-based `/aura/` entry point, and its account/authentication and duplicate-selection semantics require substantial cross-layer changes to preserve the existing personal-service workflow. PhotoPrism similarly introduces a separate account/library model. Aura instead composes mature media components with a focused catalog and client; this choice is about the desired behavior and integration, rather than the current server's storage capacity.

Official references: [Immich reverse proxy](https://docs.immich.app/administration/reverse-proxy/), [PhotoKit](https://developer.apple.com/documentation/photokit), [libvips](https://www.libvips.org/), [ExifTool](https://exiftool.org/), [FFmpeg](https://ffmpeg.org/).

## Data flow

```text
Browser files / PhotoKit original resources
  -> client SHA-256 -> prepare/resume -> durable chunks up to 128 MiB
  -> full server SHA-256 -> atomic original publication -> durable queued file
  -> ExifTool -> image previews/video covers -> duplicate/Live Photo grouping
  -> capture-date timeline, original versions, metadata and downloads
  -> on playback: inline original or short, temporary HLS segments
```

`assets/<first-two-hash-characters>/<sha256>` holds immutable originals until their confirmed permanent deletion. `aura.sqlite` stores files, logical assets, uploads, source observations, grouping keys, and user decisions. The existing decision log also retains manual primary choices, similar-pair dismissals, native album source mappings, and permanent-deletion intents and guards; their authoritative records remain in these tables. Additive, rebuildable index tables accelerate filtering, search, deletion guards and background scheduling without rewriting existing rows. `derived/` contains JPEG previews, saved covers, orientation variants and versioned DINO feature/candidate records. `incoming/` holds incomplete byte streams; `work/` holds short-lived decoding material. These paths are relative to the configurable data root. Online video segments use a separately bounded transient cache; on `nas`, its scratch directory is in `/run/aura/playback` on tmpfs and is not business data or recovery material.

The upload API identifies a byte stream by SHA-256. Chunk writes require the expected offset and flush before acknowledgment. Stale offsets return the actual offset. Completion recomputes the entire hash, verifies the expected byte count, publishes the original without replacing an existing object, and commits the file plus queue state transactionally. A retry recognizes an object published before a process interruption. Files with invalid checksums are never published. Per-original upload locks keep a slow client from blocking unrelated uploads; chunk body reads have a bounded deadline.

An existing catalog record is not sufficient to acknowledge a duplicate. Preparation and status also check that the original is a regular object of the expected size. A missing object can be recreated through the same complete-hash upload protocol while preserving its catalog identity and visibility. An existing abnormal object is reported for maintenance rather than overwritten. This availability check does not test readability or rehash every stored byte and does not replace full backup verification.

The scheduler processes independent originals concurrently, with one active attempt per hash. It fills available slots in original creation order, refills after completion or a new upload, and checks the durable queue every five seconds. Defaults allocate one job per four available CPU threads, with a minimum of one and a maximum of four; the NAS unit explicitly overrides this to eight jobs. At most four ExifTool/libvips/CPU video operations and four GPU operations run simultaneously on NAS, independently of queue length. Upload capture-date extraction shares the same CPU bound. Codec-owned thread pools also count toward the service's 1024-task budget. Catalog transactions remain serialized on the existing SQLite connection, so simultaneous exact matches publish into the same group. Acknowledged jobs survive restarts. Shutdown cancels and drains all active jobs before closing GPU workers and the database; interrupted processing returns to the queue. Command and worker-request deadlines release slots after a stalled decoder, including blocked Python request writes. APIs and downloads remain independent. No original-resolution cap is imposed; the per-file upload limit is 32 GiB and each chunk is at most 128 MiB.

Still-image derivatives use NVIDIA nvImageCodec/nvJPEG and CV-CUDA through a pool of private Python children embedded in the Go binary. JPEGs without an embedded ICC profile or CMYK components use the GPU/hybrid JPEG decoder with EXIF orientation. Other formats and profile-bearing JPEGs reuse libvips' full-resolution decoding and color normalization, then transfer RGB pixels to the GPU. Both routes use antialiased Lanczos resizing and GPU JPEG encoding for the 2560-pixel preview and 640-pixel thumbnail. RAW embedded JPEG fallbacks also attempt this GPU path. Each child handles one exclusively assigned request at a time, reuses decoder/encoder contexts across files, releases per-image buffers, and exits after 30 seconds without work. Image operations and video CUDA/NVENC share a limit of two GPU operations by default, capped by the job count. Cancellation stops only the affected image child before deletion or work-directory cleanup. The next job restarts it after an idle exit.

The GPU path limits its input to 80 megapixels to leave space for resampling and other work on NAS's 8 GiB GPU. Oversized images, unsupported operations, missing dependencies, or GPU failures use the existing CPU preview path; task details include the engine and fallback reason. This limit changes only the derivative engine and does not reject the original. Source bytes remain immutable. Canonical full-resolution pixel decoding and hashes stream the same libvips samples directly to SHA-256, retaining the same header and ICC description, preserving exact-duplicate grouping across releases; metadata and catalog updates remain CPU operations.

Video and Live Photo imports generate metadata and JPEG covers, not complete playback MP4s. Their ready state is independent of the online playback cache. A lightweight descriptor admits suitable H.264/HEVC originals, including full-range 8-bit H.264 and PCM16 audio, while retaining near-zero timestamp and zero Aura-rotation requirements. The browser tries the original when its codec hint or container MIME is supported; incomplete codec hints alone do not force transcoding. An actual playback failure, or metadata with no video dimensions, switches to HLS. Original reads support HTTP Range without recompression. Start timestamps outside the 1 ms native tolerance retain the normalized HLS timeline used by frame selection; saved Aura rotations remain pixel transformations so fullscreen and picture-in-picture keep the saved direction. [API](API.md#media) defines native eligibility.

Compatibility playback uses a finite HLS playlist and request-triggered, four-second H.264/AAC MPEG-TS segments. Browsers with native HLS support use it; other supported browsers attach hls.js to the same video element. A distant seek requests the target neighborhood rather than encoding everything before it; native HLS may first request opening segments to discover metadata. The encoder reads from the nearby source keyframe, preserves the original frame rate and applies source orientation plus the requested Aura direction to pixels. Compatible stages prefer CUDA/NVENC, with software decoding/color normalization and CPU fallback where needed. No whole-video encoder continues behind the viewer.

HDR compatibility output is BT.709 limited-range SDR. A bounded source-frame probe uses valid MaxCLL, falling back to mastering-display maximum luminance, before linearization removes that metadata. The explicit tone-map peak uses units of 100 nits, with fallback values of 100 for PQ and 10 for HLG. After full-resolution linearization, decoded frames are downsized to at most 1920 pixels per dimension before CPU float Mobius tone mapping; even dimensions and sample-aspect-ratio adjustment retain display proportions without enlarging smaller videos. This generic SDR conversion does not apply Dolby Vision RPU dynamic adjustments. Native playback can retain HDR on a capable browser and device instead. Shared diagnosis is documented in [Video playback and HDR tone mapping](https://github.com/Crashmere/agent-config/blob/main/skills/server-operations/references/common-issues.md#unnecessary-video-transcoding-and-hdr-tone-mapping).

Identical segment requests share one cancellable job keyed by original hash, direction, recipe and segment index. At most two segments generate concurrently, within the shared GPU/CPU budgets. Completed segments and generation reservations share a 256 MiB cache bound; idle entries are evicted and misses regenerate from originals. Pausing, seeking or leaving the viewer stops unnecessary fragment requests. hls.js has a short forward/back buffer; native HLS chooses its own look-ahead. Permanent deletion cancels and drains selected originals' playback jobs and evicts their segments before unlinking. Server shutdown drains playback separately from durable import jobs.

Video covers use software decoding to apply the video's display direction before GPU scaling: CUDA-decoded frames retain the display matrix, and JPEG cannot carry that matrix. Covers preserve displayed proportions and omit copied metadata so clients do not rotate them again. Cover generation falls back to CPU if GPU scaling fails. The web client versions thumbnail URLs when the generation recipe changes so cached covers do not hide rebuilt files. GPU processing affects derivatives only.

The task center expands each original into metadata, image decoding/previews/fingerprints or video cover generation, and catalog publication steps. The existing decision log holds one replaceable `media-job:<hash>` progress record per original; step boundaries and bounded media-time progress updates survive page reloads. Retrying replaces the previous attempt when work starts. Interrupted work returns to the queue and starts a fresh attempt. Step completion counts describe finished operations, while video percentages use FFmpeg output timestamps divided by source duration; neither estimates remaining wall time. Terminal tasks disappear from the paginated task center after 24 hours, while active tasks and resumable uploads remain visible. A stored activity-time projection indexes the 24-hour window without parsing all historical progress JSON on each request. The task center displays one 50-item page at a time and refreshes its current cursor.

## Catalog projections and bounded browsing

Album groups organize existing albums into single-level sections. The existing decision store holds one replaceable `album-group:<id>` record per group and one `album-grouping:<album-id>` assignment per album. Album queries resolve assignments only against active groups; deleting a group retains a tombstone and makes its albums ungrouped without changing photo memberships or originals. Group creation with albums and batch moves commit atomically. Existing decision revisions invalidate group and album summaries. The web overview supports folding sections, creating albums inside a group, and single or batch moves; native album imports retain Aura-side assignments.

The original catalog and decisions remain authoritative. Startup adds indexes and initializes missing projections for equipment values, location presence, search text, media activity and deletion guards. Database triggers queue changed metadata and DINO eligibility; background workers drain only the changed hashes. Equipment projections retain all original tags for filtering and the existing per-dimension priority tiers for dropdowns, including grouped EXIF ties and numeric zero coordinates. Filtered requests synchronize pending metadata before reading these projections. Equipment options, monthly counts and library/album summaries are cached by their corresponding revisions.

Text search keeps its literal substring behavior. Searches with at least three characters and no escaped wildcard characters use an FTS5 trigram candidate index, then apply the original escaped name/metadata predicate. Short or wildcard-containing searches retain the original scan. The dHash index divides each 64-bit value into five disjoint blocks; at Hamming distance at most four, at least one block must be unchanged. Exact distance/aspect checks remove false candidates without missing qualifying pairs.

The web gallery retains lightweight loaded catalog items and selection state, while mounting only rows within about 700 pixels of the viewport. Row spacers preserve the full loaded scroll range and restore viewer positions. Refresh reads the first page and one bounded set of mounted, selected and viewed cards rather than refetching every loaded page. Returning a card set avoids requesting full metadata for a grid update. Page merging uses ID maps. A media change outside the loaded window becomes visible when that window is refreshed.

Browser and native uploads overlap export/date/hash preparation of at most one following resource with the current transfer. The transfer protocol remains sequential, with flushed chunk acknowledgments and complete server SHA-256. Browser progress notifications are throttled and do not copy the full upload queue on every byte update; the main gallery subscribes to aggregate activity changes. Native prefetched files are removed when consumed or when their task is cancelled at the end of a pass.

## Duplicate and version rules

1. **Equal file SHA-256:** reuse the stored bytes and append the source observation. No second object is written.
2. **Equal full decoded pixels:** automatically group the files. The digest covers complete samples, their dimensions/format/interpretation, and ICC metadata. A resized thumbnail or perceptual hash never triggers this rule. If a format cannot be fully decoded, no pixel-equality claim is made.
3. **Apple content identifier or explicit PhotoKit resource group:** group the related resources into one library item. Stills and video can arrive in either order. Filenames alone are never global pairing keys.
4. **Perceptual similarity:** a 64-bit difference hash and aspect ratio propose candidates. Hamming distance at most four and aspect-ratio difference below 0.03 produce the `算法判定` review list. Candidate search uses a five-block fingerprint index and supports cursor pagination.
5. **Visual feature similarity:** DINOv2 ViT-S/14 produces normalized 384-dimensional global features from existing thumbnails, using 224-pixel center crops. Its independent persistent queue receives invalidations when files or primary/trash membership change, taking at most 16 images when a batch is full or after ten seconds from the first pending image. Upload acknowledgments, media processing and catalog publication never wait for DINO. Startup reconciles existing primary images and their derived records once. A five-minute reconciliation checks for externally changed thumbnails; idle operation does not repeatedly scan the whole library.

The DINO worker reuses one private Python process, prefers FP16 CUDA inference, falls back to CPU on CUDA failures and releases the process after 30 seconds idle. A batch shares one of the existing GPU-operation slots with image/video derivatives. It reads persistent vectors into a reusable, capacity-grown matrix, receives catalog changes after the initial synchronization, and records at most 20 nearest neighbors per processed image with cosine similarity at least 0.7. As new images arrive, their candidate edges extend the list without rerunning older images. This is a bounded incremental candidate graph rather than a continuously rebuilt global top-20 ranking. Model and preprocessing version, original hash, thumbnail size/mtime, normalized vector, neighbor scores and extraction time are flushed atomically in `derived/<hash>-dino-vits14-224-v1.json`. Failed images retain a retry record and retry after five minutes; runtime failures retry after one minute.

`智能推荐` shows DINO candidates ordered by feature similarity, with 20 pairs per page and previous/next navigation. The background worker warms candidate snapshots after catalog/review changes; requests also build a missing snapshot on demand. Candidate order is cached by catalog/review revision; repeated pages use a binary cursor lookup and return the required photo cards in the same response. A dual-handle percentage slider selects an inclusive similarity range in both the workspace and per-photo window. Two binary searches select the eligible section of the sorted snapshot before pagination and counting, without rebuilding features or changing the snapshot. List refresh preserves the current page cursor and both bounds; switching review sources or changing the range returns to the first page. It filters against current primary membership, trash/deletion state and shared dismissal decisions, and excludes pairs already passing the dHash rule. Feature scores are not duplicate probabilities. Both lists require a user decision to merge or dismiss; dismissals are durable and reversible, and never change original storage. Permanent deletion cancels the relevant DINO batch, drains it and removes only the selected hashes' feature records alongside their derivatives.

The default primary prefers images over videos and ranks resources by resolution, metadata completeness, GPS/date availability, and native-original preference until the user explicitly selects an image or video version. That choice is retained in the decision log and respected by reprocessing and grouping while the chosen resource belongs to the resulting item. A primary still's catalog motion uses the same unique native pairing rule as the viewer and rotation editor, so choosing another Live Photo retains that still's own motion rather than the group's highest-ranked video. Unrelated or ambiguous videos remain retained resources without supplying a fallback pair. Metadata from all retained versions remains available; the detail response provides a combined view with the higher-ranked version winning duplicate keys. The original file is never rewritten to synthesize metadata.

Library selection, similar candidates and comparisons between distinct items share a merge dialog that lets the user select either displayed primary before confirmation. Resource transfer, the union of album memberships and the selected primary decision commit together; an invalid chosen hash rolls back the complete operation. The retained logical ID is independent of which input supplies the primary. Comparing versions of the same item does not offer another merge.

The viewer loads details for multi-version items and offers a thumbnail selector for their image versions, or video versions for video items. Viewing a version changes only the current preview, dimensions and metadata; setting the library primary remains a separate write. Preview choices are remembered while that viewer stays open. Live Photo playback selects the video's matching Apple content identifier, or an unambiguous original/edited PhotoKit resource pair within the exact source group when content identifiers are absent. A filename or another group's motion resource does not supply a fallback pair. Individual videos can also be opened from the resource list.

The viewer can preview and save quarter-turn rotations for the selected photo or video version. Each original hash has one replaceable rotation decision in the existing catalog; it follows that resource through merge/split operations. A photo's exact, unambiguous native motion resource receives the same rotation delta, preserving any independently saved motion offset. Save builds the required browsing variants before committing both decisions together and rejects stale directions or changed resource membership. Originals, canonical fingerprints, source metadata and automatic grouping remain unchanged.

Saved JPEG browsing variants preserve compressed pixels and receive an EXIF orientation tag. They always derive from unedited previews, so repeated rotations do not accumulate compression loss. Source-size/mtime markers detect regenerated base derivatives; missing or stale variants rebuild on access. These CPU metadata operations need no pixel decoding or new dependencies. Video rotation is applied to requested HLS segments, including native fullscreen and picture-in-picture, without generating a complete rotated MP4. Saving a direction prepares only the required JPEG previews before committing. The gallery, albums, comparison and viewer use rotation-specific media URLs; unsaved editor previews use CSS rotation. Original downloads remain byte-identical, with saved directions retained in the ZIP catalog manifest.

Videos support a manually selected cover, and a Live Photo can display a frame from its exact native motion as its key photo. The frame editor previews the timeline before save and can restore the source still or automatic video cover. Each owner hash has one replaceable cover decision in the existing catalog. Its video, actual frame timestamp, native display dimensions and revision identify independent thumbnail/preview files; it does not create or replace an original, alter the primary resource, or change canonical grouping. A saved selection follows its owner while its motion remains in the same item. Reprocessing leaves the selection and canonical derivatives separate, and missing cover files regenerate from the decision and immutable motion.

Frame selection resolves original presentation timestamps rather than rounding an interior time forward. A bounded CPU scan begins at the preceding keyframe and stops after the following displayed frame, preserving variable-rate and nonzero-start timing. FFmpeg applies the source display matrix during compatible software decode, then prefers CUDA resizing with the existing shared GPU slots and CPU fallback. Save prepares both cover files, rechecks the native pair, saved directions and previous revision, then commits the decision. Permanent cleanup cancels/drains frame work against both original hashes. Cover-specific URLs and decoded-preview identities keep gallery, albums, comparison, video posters and the viewer consistent after save/reset; Aura rotation applies to the selected frame without recompressing it.

Native adjustment records are decoded on detail requests from immutable XML-plist originals, including their complete compressed JSON arrays. The information panel associates them with the selected resource's source and summarizes recognized active crop, trim, Live Photo cover, depth, portrait-lighting, tone, color, definition and sharpening settings. It preserves raw parameters for inspection and identifies unsupported private formats. Crop percentages use the record's master coordinate dimensions; numeric strengths and angles retain recorded units rather than imitating Apple's UI sliders. Camera-generated treatments are attributed to Apple Camera, and record timestamps are not presented as an Aura user-action history.

All retained byte-distinct versions remain downloadable. A user can select another primary, split a resource, or restore an item from recently deleted. A split preserves the source item's trash state and album memberships; processing retries respect explicit grouping decisions. A later import can discover compatible exact relationships again. Source observations and merge/split decisions are retained for diagnosis.

Automatic grouping does not merge existing active and trashed groups or transfer their visibility by overwriting a conflicting group key. A newly arriving native resource can join its existing source's trash group without restoring it. Manual merge across active/trash states returns a conflict; the user must first make their visibility consistent. Processing reads current group identity at publication rather than restoring a cached identity after a concurrent merge or split.

Uploading an original whose item is in recently deleted does not restore it automatically. The upload response identifies that state so the web interface can offer an explicit restore action or open the existing item.

The web navigation separates automatically combined photo versions (`照片版本`) from user merges (`手动归并`). Both categories require multiple image resources; paired video and adjustment data are counted separately as resources. Classification reads existing merge decisions and current original membership, rather than trusting an asset ID that can change during grouping. A manual merge takes precedence while its moved images and an image from the other side still belong to the same item. Details identify native original, edited, motion and adjustment resources using their PhotoKit resource types. These read-only projections do not change membership or original bytes.

The similarity tabs display the total number of candidate pairs from each source after visibility and dismissal rules, independent of pagination. Counts reuse the existing fingerprint index and DINO snapshot and refresh with the review revision. Candidate cards show complete decoded photo proportions.

The comparison dialog displays current primary previews at full proportions in side-by-side, swipe overlay or full-frame A/B views. Ordinary wheel input uses the viewer's 1–5× zoom range and response; dragging a zoomed photo moves both previews together. The switch-version button and unmodified `V` shortcut toggle the two full-frame previews while both remain mounted, preserving the shared zoom and pan position. Each photo stays clipped to its viewport, and the overlay divider moves independently. Photo dialogs lock background scrolling until the last viewer or comparison closes, then restore the previous page position. Text input, IME composition and modifier shortcuts retain their normal behavior. Browsing comparisons does not change originals, version choices or grouping.

`整理记录` retains two recovery paths across browser reloads: effective `已确认不同` pairs can be undone, and `分离记录` can return the recorded original to its former item. Restoring a split moves that hash alone, preserves unrelated originals and current trash state, adds the album memberships, and records completion in the existing decision log. Restoration follows recorded merge destinations when the parent ID changes. New split records also retain an original-hash anchor, usable while that anchor has not been split again. Changed or removed targets and newer splits show a conflict reason. Recovery runs only after the user selects the corresponding record, and completed split restorations are omitted from the pending list.

## Deletion

Normal removal updates the logical item's trash timestamp and preserves every original and membership. Restore reverses that visibility change. Batch removal and restore validate all selected IDs in one transaction; a failed batch does not partially update the catalog. List, album, month, and library counts refresh together after mutations, including uncertain request failures. Recently deleted has no automatic expiry or purge.

Permanent deletion is available only for explicitly selected trash items and requires a second confirmation. The server first commits a cleanup request in the decision log. That request identifies the selected logical items, exact original hashes, eligible source guards, and planned original bytes. It immediately blocks restore, grouping changes, uploads, processing, and media access for the affected resources. The worker then cancels and drains targeted processing, removes their original objects, derivatives, matching incoming chunks and proven work links, flushes affected directories, and removes catalog rows and memberships before recording completion. The intent survives failure or restart, so partial cleanup remains pending and can resume rather than being reported as complete. Upload and processing locks coordinate on each original hash; no SQLite transaction waits while acquiring those locks.

Completed requests retain minimal hash/source guards to prevent continuous import from recreating deliberately removed items. A source-wide guard is recorded only when no retained file or upload outside the selection still uses that source; shared sources from explicit splits are not grounds to remove or exclude the retained items. Resources already covered by another confirmed cleanup request do not count as retained, but their IDs, hashes, and bytes remain owned by that request. A scoped source rejection must not become a hash rejection for the same bytes retained under another source. The decision records remain authoritative; indexed hash/source guards and pending-asset projections accelerate checks while retaining the cleanup history.

The web interface confirms permanent deletion in a separate dialog listing the selected items and their resources. The explicit confirmation button submits the existing confirmation token; no text entry is required. Cancel, Escape, and closing the dialog submit no deletion request.

Permanent deletion applies to the live Aura library, not system Photos, existing backup packages, browser caches, or downloads already in progress. It unlinks live files; it is not a secure-erase operation or a guarantee that the filesystem immediately releases the reported byte count. An older recovery point can contain the removed originals and older deletion history; production restoration remains an explicitly selected maintenance operation.

## Albums

Albums organize logical assets through `albums` and `album_assets` in the existing catalog. One item may belong to multiple albums; adding it again is idempotent. Creating an album with selected assets and changing membership each use a transaction, so an invalid or recently deleted asset rejects the complete addition. Names are trimmed and limited to 100 Unicode characters; each write accepts at most 1000 assets.

Single-level album groups, assignments and their explicit order are replaceable records in the existing decision log. The album overview supports individual or selected-batch movement into a group or the ungrouped section through the transactional move endpoint. Mouse dragging uses the card surface; touch dragging starts after a stationary 350 ms press, preserving ordinary taps and scrolling. Group handles insert a group before or after the target section's midpoint. Same-group moves and unchanged group orders send no write. Unranked groups follow the saved order in creation order; group deletion leaves albums and photo memberships intact.

Dragging lifts a full card preview while fading its source, and the target group gradually shows an accent outline and the exact cue `松开以移入此分组`. Release displays the final membership or group order immediately and saves it in the background; failure restores the confirmed layout and refreshes the catalog. The moved card settles only at its destination, while neighboring cards and group headers shift independently rather than carrying it through the source group's position. A collapsed target stays collapsed and receives a count cue. Pointer capture, movement thresholds, edge scrolling and Escape cancellation keep dragging separate from opening an album. Completion, cancellation and leaving the view clean up previews and animations. Reduced motion retains color and target feedback without translation, rotation or scaling.

Albums use the newest visible member as their automatic cover. Inside an album, the bottom selection toolbar assigns the selected member as the cover; the action is enabled only for exactly one selected item and submits directly without another picker. The cover API can also restore automatic selection. The existing decision log stores the chosen member's original hash, so the selection follows regrouping without a schema change. Album cards use that item's current thumbnail, saved rotation and video-cover or Live Photo key-photo revision; selecting a video reuses its cover without generating another image or changing its original. A selected member outside the album or in recently deleted temporarily falls back to the automatic cover; restoring membership or visibility makes the selection effective again. Permanent removal of the anchored original leaves the automatic fallback.

Dropping external files inside an album captures that album in each browser queue entry. Original acceptance can precede logical item publication; upload-status polling runs independently of subsequent file transfers and adds each published item through the existing membership endpoint before reporting that entry complete. Near-simultaneous completions share a short browser refresh window; no album addition waits for the upload batch to finish. An addition failure remains retryable; retry reuses the accepted original. Filtered and recently deleted items are not added or restored. Queue deduplication includes the target album, so the same file can be added to another album without storing another original. Navigation after the drop does not change the queued target.

Album browsing reuses capture-date pagination, filename/metadata search, and date filters. Recently deleted items retain membership but disappear from album counts, covers, and ordinary browsing; restoration makes them visible again. Removing membership or deleting an album leaves the assets and original files unchanged.

The common asset query returns album IDs and names together with each photo card, avoiding per-photo membership requests. Shared badges display these memberships in the library, Live Photos, videos, automatic versions, manual merges, multi-version items, similar candidates, the viewer and both comparison sides. Inside an album, the current-album context hides only that album's badge while retaining other memberships. Badge strips scroll horizontally within their existing tile or header bounds without changing the virtualized grid geometry.

All merge paths transfer the union of the two items' album memberships before removing the redundant logical asset. A split inherits the source item's memberships for the new item while retaining the source's memberships. These rules also apply to automatic exact-match and Live Photo grouping.

The web navigation uses albums instead of favorites. The photo viewer opens the album chooser from its More menu, and the library supports batch addition. The chooser can create an album and add the selected items in one transaction. An album's photo picker excludes existing members and retains selections across searches and pages. The legacy favorite field and upload hints remain for client/data compatibility, without favorite controls or badges in the web interface.

The library filter panel includes album membership: all items, members of any album, or items belonging to none. Legacy `unfiled` URLs and the prior browser preference migrate to the equivalent membership filter. Applying filters resets pagination and selection; membership changes refresh the filtered results without changing originals.

Optional native album import uses a stable client-library and PhotoKit collection source key. It adds already uploaded, visible items to the mapped Aura album in bounded transactions. It neither removes memberships nor propagates Photos deletions, and it preserves an Aura user's album rename. An explicitly deleted mapped album is not silently recreated.

## Browsing and task state

Search and filter updates within the same library section and album retain current photo nodes until the replacement page arrives. The gallery marks the pending update with reduced opacity and suspends actions on previous results; failures retain the photos beside a retry message. Section or album changes still establish a new data scope. Follow the shared [refresh diagnosis](https://github.com/Crashmere/agent-config/blob/main/skills/server-operations/references/common-issues.md#a-data-refresh-flashes-or-resets-the-page).

Library views, album selection, search, date filters, and the open photo are represented in browser URLs. Opening a photo adds a history entry; switching photos replaces that entry, so Back returns to the library. Switching library sections clears filters. The floating filter panel holds a draft until Apply; Cancel leaves the current results unchanged. Its dimensions cover media kind, original format, orientation, location, image versions, album membership, capture/import dates, camera/lens, primary resolution/size, and processing status. Assets and month counts share server-side filtering before pagination; the month picker omits capture-date bounds while retaining all other conditions. The API reference defines each dimension's resource scope. Device and lens selectors load deduplicated options from all retained library originals, including secondary resources and recently deleted items, whenever the panel opens. They use exact metadata matches; existing text-filter URLs retain substring behavior.

The browser keeps a default thumbnail size with three smaller and three larger steps. On first use, an existing saved size becomes that browser's centered default; a new browser starts at seven columns above 720px and four on smaller screens. The mobile range stops at one column when fewer than three larger steps are possible. The browser retains both its default and subsequent size adjustments across reloads; double-clicking the slider restores its default. Layout changes animate visible photo containers while anchoring a visible photo, and honor reduced-motion preferences. Dense layouts suppress crowded badges without changing selection or media data.

The aspect-ratio button beside thumbnail zoom switches between square crops and complete images centered in the same grid cells. Square mode is the default; the browser remembers the chosen mode across views and reloads. Decoded thumbnail dimensions determine the displayed ratio, including EXIF rotation. Both directions use the same 280ms frame transition and retain one image-fit mode, so the crop changes continuously instead of jumping when a toggle changes the layout. Media badges and selection controls follow the image bounds. Reduced-motion preferences disable this transition.

Selection mode supports individual photos, Shift ranges, and reversible day-group selection. Ctrl/Command-click on the media or its surrounding tile enters selection mode and toggles that item instead of opening the viewer. Select-all applies to loaded items and excludes pending permanent deletions. Background processing refreshes preserve the loaded range and reconcile selections; pagination failures pause automatic requests until retry. The viewer shows the loaded position and nearby thumbnails and loads another catalog page near the current boundary. Photos first display the existing 640-pixel thumbnail, then crossfade to the 2560-pixel preview after decoding. The image keeps its geometry when the overlay controls are hidden. A single tap toggles controls; double tap/click and pinch zoom around the contact point, dragging pans a zoomed image, horizontal swipes navigate, and downward swipes at fit size dismiss the viewer. Ordinary wheel and trackpad scrolling over the photo stage zoom between fit and five times fit, without scrolling the background page. The viewer locks page scrolling until it unmounts, then restores the pre-open scroll position; the details panel keeps its own scrolling. A/Left Arrow and D/Right Arrow navigate to the previous and next media, while text input, composition, modifier shortcuts, and range controls retain their own behavior.

Media loading follows a browser-local `auto`, `save`, or `quality` preference. Automatic mode defers the clear photo until requested or zoomed when Save-Data or a 2G connection is reported; other connections load the current clear photo normally. Save mode defers that request on every connection. Adjacent prefetch waits for the current clear photo, runs sequentially for at most two neighbors, and stops on slow connections, Save-Data, offline state, backgrounding, or video playback. A deliberate thumbnail hover can warm its preview. Navigation cancels obsolete speculative loads, and rapid intermediate items delay their clear-photo request. At most three decoded previews are retained; compressed media uses the browser's private HTTP cache. Browser connection information is optional, so the manual preference remains available in the viewer's More menu. Metadata details are fetched when the information panel opens, with obsolete requests aborted.

Videos and Live Photo motion use the same player. A normal video has only a poster until explicit playback; neighboring videos and originals are never prefetched. Preparation fetches only the playback descriptor and, for HLS, its playlist. Playback exposes progress, buffered ranges, seeking, ten-second jumps, speed, volume, fullscreen, and picture-in-picture where supported. Space toggles playback, J/L seek, M toggles mute, and F opens fullscreen. Controls hide after inactivity during playback. Leaving an item pauses and unloads its video; backgrounding pauses playback except for picture-in-picture. Saving the current video's direction preserves position, speed and pause state when rebinding its source. Mobile Safari can use its native fullscreen player. Delivery follows the original-first and temporary-segment paths described above, without an adaptive-bitrate ladder.

The task center reads durable file processing records and incomplete upload sessions, with cursor pagination and status filters. File status distinguishes accepted originals from pending, failed, and ready browsing resources. Retry queues metadata and derivative processing without changing original bytes; incomplete uploads require the client to reselect or recover the source bytes. Error messages remain available independently of the in-memory browser upload queue. A transient image-loading failure has a retry path instead of being presented indefinitely as server processing.

Whole-application NAS backup and recovery are agent-operated through server-operations. Aura's web application has no backup status card, backup archive controls, or dependency on Portal recovery APIs; Portal remains responsible for device authentication.

## Date selection and continuous import

The server extracts capture dates from original EXIF/QuickTime metadata; native PhotoKit capture dates and file modification times provide fallbacks. A missing timezone uses the configured runtime timezone. Date ranges are inclusive calendar dates. Browser batches transmit the selected range; the server checks the original capture date before publishing, discarding only out-of-range temporary uploads. Photos with missing capture metadata fall back to the provided file date.

Chrome can retain a user-authorized directory handle and check it every 30 seconds while the page remains running. A browser restart requires reconnecting the handle or reselecting files; existing server offsets remain reusable. Browser selection does not grant background access to the iOS system photo library.

The Apple companion queries PhotoKit by creation date and exports each `PHAssetResource` without conversion. It handles iCloud originals under the user's network and power policy. A stable client source ID plus PhotoKit asset ID pairs resources, and receipts avoid re-exporting completed, unchanged resources. Normal processing-status refreshes and album imports can invalidate a receipt only after a confirmed missing or incomplete original, allowing reupload without discarding receipts on authentication or network failures. Original availability investigations and post-recovery receipt reconciliation are agent-operated. The server still performs SHA-256 checks for every new transfer. iOS scheduling and application signing constraints are documented in [Apple](APPLE.md).

## Media fidelity

Original HEIC, RAW, JPEG, video, ICC, EXIF, GPS, embedded metadata, and native adjustment resources retain their uploaded bytes. JPEG previews use a maximum dimension of 2560; thumbnails use 640; temporary H.264/AAC video segments use a maximum dimension of 1920 without enlarging smaller source videos. Direct original playback retains its source resolution and color format. These limits affect browsing only. Unsupported RAW decoders may use the embedded camera JPEG for a preview, while retaining the full RAW original. Such embedded previews are excluded from automatic pixel-equivalence decisions.

Browser or operating-system conversion that occurs before Aura receives a file cannot be reversed by the server. Use PhotoKit or exported unmodified originals when preservation is required. Downloading a Live Photo returns a ZIP with every resource and an `aura.json` source manifest; saving a ZIP in an iOS browser is not a native Photos-library import operation.
